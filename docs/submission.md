## Project name

Reliquary

## Tagline

A skeleton kit for resurrecting dead software — and proving nothing was lost.

## Category

Skeleton Crew

## Inspiration

Every small archive, parish council and scrapyard in the country is sitting on a
dead system: a `.dbf` export nobody can open, a card index, a dot-matrix ledger.
The data is fine. The software is gone.

Rebuilding an interface is the easy part. **Trusting the migration is not.** These
records stay dead because nobody can prove a rebuild didn't quietly drop 300 rows.

## What it does

Reliquary is a lean template for wrapping a dead data source in a modern web
interface, with one non-negotiable promise: lossless, or it tells you exactly what
it lost.

- **A three-method contract.** Any legacy source implements `count()`, `scan()` and
  `normalise()`. That is the whole adapter surface.
- **A Resurrection Report.** Every import produces records in, records out, field
  mappings, unmapped fields, and every rejected row with a reason. `rowsIn` must
  equal `rowsOut + rejected`, or the build refuses to publish.
- **Three shared screens.** Search, Record and Report, themed per app, never forked.

## Two applications from one foundation

**Card Catalogue** — a volunteer local-history society with 2,000 index cards from
a 1994 dBase export. Search-first: surname, street, shelfmark. Every field carries a
provenance stamp showing which legacy column it came from. The report reads
`2000 in / 1997 out / 3 rejected / LOSSLESS`. A printable request slip falls out of
any record.

**Parts Ledger** — a motor factor acquires a rival scrapyard and inherits 1,200 lines
of dot-matrix stock ledger with no one who understands it. Task-first, not
search-first: pick a bin range, walk 228 entries, count each one, record every
discrepancy with a note and initials. Same Report component, opposite question —
not "did the import lose rows" but "does the ledger match the shelf".

## How we built it

TypeScript throughout, npm workspaces, React + Vite, Vitest and fast-check.
Both apps build to static assets. Datasets are generated by committed, seeded
scripts, so a judge can regenerate them byte-identically.

The adapter contract is enforced by property-based tests: scan length equals count,
identifiers survive normalisation, and the reconciliation equation holds for any
generated mix of valid and broken rows.

## How Kiro was used

_(see README → "How Kiro was used"; summarised here)_

Steering documents were written before the requirements, which is what turned
"lossless migration" from an aspiration into a testable invariant. Kiro then
implemented each task from `.kiro/specs/reliquary-kit/` in a scoped, headless run —
one run per task group — with a commit between each.

Kiro wrote the contract, the pipeline, the publish guard, the repository, the UI
shell, both adapters and the property-based suite. It also diagnosed and fixed its
own bug: `configureGlobalConfig` does not exist in fast-check 3.x, found by running
the suite rather than reading its code.

Human work: the static checks. `tsc` caught a `maxSize`/`maxLength` mix-up that left
tests green while types were wrong; screenshots caught three layout failures the
suite was indifferent to.

## Challenges

The hardest part was refusing to make the report decorative. A badge that says
"lossless" is worth nothing if it can be set by hand, so `status` is computed from
the counts and `publish()` throws on a mismatch. That one decision forced the
adapter contract to stay small and the UI to tell the truth.

reconciliation, rather than our sample data.
